# فاز ۲ — Generics پیشرفته

این درسنامه برای Java 21 است. generic در منبع نوع را نگه می‌دارد و در bytecode آن را پاک می‌کند. امضایی که این پاک شدن را ندیده باشد، یا کامپایل نمی‌شود یا در زمان اجرا دروغ می‌گوید.

## چرا این‌طور کار می‌کند

type erasure یعنی پارامتر نوع، بعد از کامپایل، به حدش تبدیل می‌شود: بدون حد به `Object`، با حد به همان حد. به همین خاطر دو overload مثل `m(List<String>)` و `m(List<Integer>)` یکی هستند و کامپایلر ردشان می‌کند. `instanceof List<String>` هم غیرقانونی است، چون در زمان اجرا `String` آن‌جا نیست. چیزی که می‌توانی بپرسی `instanceof List` است، و آن فقط خام بودن لیست را می‌گوید، نه نوع عنصر را.

bounded type parameter، مثل `<T extends Number>`، هم در منبع جلوی نوع غلط را می‌گیرد و هم حد erasure را `Number` می‌کند. داخل متد می‌توانی با `T` مثل `Number` کار کنی، نه بیشتر.

wildcard جهت داده را بدون اسم گذاشتن روی نوع می‌گوید. `List<? extends Number>` تولیدکننده است: بیرون آوردن به‌صورت `Number` امن است، گذاشتن عنصر (جز `null`) امن نیست، چون نوع واقعی شاید `Integer` باشد و تو `Double` بگذاری. `List<? super Integer>` مصرف‌کننده است: `Integer` را می‌توانی بگذاری، ولی بیرون آوردن فقط `Object` است. این همان PECS است: producer-extends، consumer-super.

فرق سه‌تایی این است. `List<String>` دقیقاً لیست رشته است و به‌خاطر invariance نه `List<Object>` است و نه برعکس. `List<?>` لیستی از یک نوع ناشناس است. capture یعنی کامپایلر برای آن `?` یک نوع تازه و یکتا می‌سازد. چون آن نوع را نمی‌شناسی، نمی‌توانی `String` را داخل `List<?>` بگذاری، حتی اگر حدس می‌زنی رشته است.

heap pollution وقتی است که از راه raw type یا cast بدون چک، عنصری با نوع غلط وارد ساختار generic شود. کامپایلر هشدار unchecked می‌دهد. خطا همان لحظه دیده نمی‌شود؛ بعداً موقع خواندن، `ClassCastException` می‌آید. `@SuppressWarnings("unchecked")` هشدار را پاک می‌کند، نه آلودگی را.

پارامتر نوع را وقتی بنویس که خود متد باید آن نوع را برگرداند یا دو جا را به هم وصل کند. wildcard را وقتی بنویس که صدازننده نباید نوع را نام‌گذاری کند و تو فقط می‌خوانی یا فقط می‌نویسی.

آرایه reify می‌شود و نوع اجزایش در زمان اجرا هست. generic نه. برای همین `new T[]` و `new List<String>[n]` ساخته نمی‌شوند: کامپایلر نوعی را که پاک شده نمی‌تواند در آرایه نگه دارد، و اگر می‌توانست، store چکِ آرایه دروغین می‌شد. آرایهٔ generic را یا صدازننده می‌دهد، یا با `IntFunction<T[]>` ساخته می‌شود.

bridge method پلی است که erasure بین امضای فرزند و والد لازم دارد. مثلاً `Comparable<String>` در منبع `compareTo(String)` دارد، ولی اینترفیس خام در bytecode متد `compareTo(Object)` می‌خواهد. کامپایلر یک متد synthetic می‌سازد که cast می‌کند و متد واقعی را صدا می‌زند. با `javap -c -p` دیده می‌شود. خودت نمی‌نویسیش.

## قاعده

در API، سمتی که داده بیرون می‌دهد `? extends` است و سمتی که داده می‌گیرد `? super`. جایی که هر دو کار را با همان نوع می‌کنی، پارامتر نوع بگذار، نه wildcard. raw type را برای ساکت کردن کامپایلر به کار نبر. هشدار unchecked یعنی یک cast را خودت گردن گرفته‌ای.

## مثال

یک انتقال کوچک. مبدأ فقط تولید می‌کند، مقصد فقط مصرف می‌کند، و `T` این دو را به هم وصل می‌کند:

```java
static <T> void transfer(List<? extends T> from, List<? super T> to) {
    for (T item : from) {
        to.add(item);
    }
}
```

`instanceof` فقط تا حدی می‌رسد که erasure نگه داشته. `instanceof List<String>` کامپایل نمی‌شود. چک قانونی، نوع عنصر را برنمی‌گرداند:

```java
static Object first(Object value) {
    if (value instanceof List<?> list && !list.isEmpty()) {
        return list.get(0);
    }
    return null;
}
```

## اشتباه رایج

`List<String>` را با cast به `List<Object>` دیدن، یا برعکس، تا بتوانی هر شیئی را `add` کنی. کامپایلر اگر خام یا unchecked باشد کوتاه می‌آید، و اولین `get` که انتظار `String` دارد می‌ترکد.

## تمام است وقتی

یک API کوچک بنویسی که تولیدکننده و مصرف‌کننده را با `? extends` و `? super` جدا کرده باشد.
