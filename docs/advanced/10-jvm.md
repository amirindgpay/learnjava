# فاز ۱۰ — JVM

این درسنامه برای Java 21 است. از bytecode تا GC، کار تو نام بردن پرچم نیست. کار تو این است که بدانی چه را نگاه کنی تا بین «کند است» و علت فرق بگذاری.

## چرا این‌طور کار می‌کند

کلاس قبل از اجرا بار می‌شود. bootstrap class loader هستهٔ `java.base` را بار می‌کند و والد ندارد. platform class loader بقیهٔ ماژول‌های سکو را. application class loader کلاس برنامه و classpath را. قاعدهٔ پیش‌فرض واگذاری به والد است: اگر والد کلاس را بشناسد، فرزند دوباره تعریفش نمی‌کند. برای این مسیر همین سه نام و همین ترتیب کافی است.

linking بعد از بار شدن است و سه اسم دارد. verification یعنی bytecode از قواعد ایمنی JVM خارج نیست. preparation یعنی حافظهٔ فیلدهای static گرفته می‌شود و مقدار پیش‌فرض می‌گیرد، نه مقدار مقداردهندهٔ منبع. resolution یعنی ارجاع نمادین کلاس و متد به ارجاع مستقیم بدل می‌شود، و اغلب تا اولین استفاده عقب می‌افتد. لازم نیست این سه را در کد جدا کنی. لازم است بدانی خطای `VerifyError` و `NoClassDefFoundError` این مرحله‌اند، نه «خراب شدن جاوا».

`javap -c -p` bytecode متد را نشان می‌دهد. این‌ها را به‌عنوان واژهٔ مسیر صدا بشناس، نه دستور حفظی. `invokespecial` سازنده، متد private، و `super` را صدا می‌زند. `invokevirtual` متد نمونه را با نوع واقعی شیء انتخاب می‌کند. `getfield` فیلد نمونه را از روی شیء می‌خواند. `ldc` یک ثابت را از constant pool روی پشتهٔ عملوند می‌گذارد. اگر این چهارتا را در یک متد کوچک پیدا کنی، مسیر صدا را خوانده‌ای.

هر فراخوانی یک stack frame دارد: متغیر محلی و پشتهٔ عملوند. شیء با `new` روی heap است. متغیر محلی فقط ارجاع را نگه می‌دارد. garbage collector شیئی را جمع می‌کند که از ریشه (پشتهٔ نخ‌های زنده و static) دیگر به آن نرسی. در جاوا `free` نمی‌نویسی.

جمع‌کننده در Java 21 چندتاست. Serial برای heap کوچک و یک نخ. Parallel برای توان عملیاتی، با چند نخ در خود GC. G1 پیش‌فرض است و heap را ناحیه ناحیه جمع می‌کند تا مکث را کوتاه‌تر از یک جمع کامل نگه دارد. ZGC را وقتی تأخیر مهم‌تر از سادگی پیش‌فرض است انتخاب می‌کنی. stop-the-world یعنی در بخشی از چرخه، نخ‌های برنامه ایستاده‌اند. G1 و ZGC این مکث را کوچک می‌خواهند. حذفش نمی‌کنند.

GC وقتی مسئلهٔ برنامه است که نرخ allocation از آنچه چرخه می‌تواند پس بگیرد جلو بزند، یا مکث و زمان CPU جمع‌کننده در GC log بخش جدی اجرا باشد. ساختن شیء کوتاه‌عمر به‌خودی‌خود باگ نیست. باگ این است که بدون لاگ، هر کندی را به GC نسبت بدهی.

JIT کد داغ را به کد ماشین بدل می‌کند. در compilation لایه‌ای، متد اول تفسیر می‌شود، بعد C1 سریع و با بهینه‌سازی کمتر کامپایلش می‌کند، و اگر هنوز داغ باشد C2 وقت بیشتری می‌گذارد و کد تندتر می‌سازد. warmup یعنی همین فاصله تا C2. deoptimization یعنی فرض JIT باطل شده، مثلاً کلاس جدیدی بار شده که یک صدا را از تک‌ریختی انداخته، و اجرا به مفسر برمی‌گردد. اندازه‌گیری را قبل از warmup با بعدش یکی نکن.

تداخل نسخه وقتی است که دو JAR همان کلاس را با شکل متفاوت دارند. classpath اولین نسخه‌ای را که پیدا کند بار می‌کند و دومی را بی‌صدا نادیده می‌گیرد. علامت معمولش `NoSuchMethodError` یا رفتار کهنه است، نه یک خطای قشنگ «نسخه غلط است». روی module path، بستهٔ شکافته بین دو ماژول خطا می‌دهد. این یکی از دلیل‌های مرز ماژول است.

در پروفایل چهار جا را از هم جدا کن. CPU: کدام متد وقت می‌گیرد. allocation: چه چیزی ساخته می‌شود و چقدر. lock: کدام قفل نخ را معطل کرده. thread dump: نخ‌ها کجا ایستاده‌اند و deadlock هست یا نه. GC log: مکث، حجم آزاد شده، و نرخ allocation. `jcmd` برای یک نگاه زنده به فرایند است، مثل dump نخ یا خلاصهٔ heap. JFR برای ضبط یک بازه است، تا همان چهار چیز را در طول زمان ببینی. پرچم‌ها را حفظ نکن. منبع را انتخاب کن: عکس لحظه، یا ضبط.

## قاعده

کندی را به یک منبع مشاهده وصل کن، نه به یک حدس. مسیر صدا را با `javap` بخوان. شیء را روی heap و ارجاع را روی stack جدا کن. اگر کلاس پیدا نشد یا متد با نسخه نمی‌خواند، اول ترتیب classpath و تکرار کلاس را ببین.

## مثال

یک متد کوچک و چیزی که در `javap -c -p` باید پیدا کنی: `invokespecial` برای سازنده، `getfield` برای خواندن فیلد، `invokevirtual` برای `trim`:

```java
String cleaned(Book book) {
    return book.title().trim();
}
```

اگر `title` یک `record` accessor باشد، در bytecode هنوز یک صدا زدن متد است، نه خواندن فیلد public. اسم دقیق دستور را از خروجی همان کلاس بردار. حفظ کردنش لازم نیست.

برای «وقت کجا رفت» یکی از این دو منبع کافی است. thread dump نشان می‌دهد نخ‌ها داخل کدام متد ایستاده‌اند. GC log نشان می‌دهد مکث و حجم جمع‌شده چقدر از زمان را برده. اگر dump آرام است و GC log شلوغ، مسئله حافظه است. اگر GC log آرام است و یک متد در بالای CPU است، مسئله آن متد است.

## اشتباه رایج

یک بار اجرای اول را کند دیدن و نتیجه گرفتن که الگوریتم بد است. آن زمان ممکن است warmup باشد: تفسیر و C1، قبل از اینکه C2 متد داغ را کامپایل کند.

## تمام است وقتی

با `javap` مسیر یک فراخوانی را در bytecode نشان بدهی، و از روی thread dump یا GC log بگویی وقت یا حافظه کجا می‌رود.
