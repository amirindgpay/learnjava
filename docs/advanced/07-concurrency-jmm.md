# فاز ۷ — Concurrency و Java Memory Model

این درسنامه برای Java 21 است. همزمانی سه سؤال جداست: آیا نوشتنِ نخ دیگر را می‌بینی، آیا این قدم یک‌پارچه است، و کار را با چه مدلی اجرا می‌کنی. قاطی کردن این سه تا، هم برنامه را خراب می‌کند هم توضیح را.

## چرا این‌طور کار می‌کند

Java Memory Model می‌گوید بدون رابطهٔ happens-before، یک نوشتن در نخ دیگر لازم نیست دیده شود. کامپایلر و CPU مجازند خواندن و نوشتن را جابه‌جا کنند. happens-before این دیده‌شدن را تضمین می‌کند: ترتیب برنامه داخل یک نخ، باز کردن قفل بعد از بستن همان monitor، نوشتن `volatile` قبل از خواندن بعدی همان متغیر، `start` قبل از کارِ نخ، و تمام شدن نخ قبل از برگشت `join`.

visibility یعنی آخرین نوشتن را ببینی. atomicity یعنی عمل وسطش پاره نشود. `volatile` برای یک خواندن یا نوشتن، هر دو را برای خود آن متغیر می‌دهد (از جمله `long` و `double`). برای `count++` کافی نیست، چون آن خواندن، جمع، و نوشتن سه عمل است. دو نخ می‌توانند یک مقدار را بخوانند و هر دو همان حاصل را بنویسند. اینجا یا `synchronized` لازم است، یا کلاس atomic مثل `AtomicInteger`.

`synchronized` هم مانعهٔ همزمانی است هم happens-before. ورود به monitor، نوشتن‌های قبلیِ کسی که قفل را رها کرده می‌بیند. قفل را روی همان شیئی بگیر که از وضعیتش محافظت می‌کند، نه روی یک شیء تازه‌ساختِ بی‌ربط.

`ReentrantLock` همان نقش را با امکان اضافه دارد. `tryLock` اگر قفل آزاد نباشد منتظر نمی‌ماند، پس می‌توانی به‌جای گیر کردن یک کار دیگر کنی. `unlock` را در `finally` بگذار. فراموش کردنش قفل را تا آخر عمر برنامه نگه می‌دارد. `Condition` جای `wait` / `notify` روی همان قفل است: `await` قفل را رها می‌کند تا `signal` بیاید، و باید قفل را از قبل داشته باشی. برای این مسیر، دانستن همین نقش کافی است. پروتکل‌های ظریف `wait` را از صفر ننویس.

ساختارهای همزمان، قفل بیرونی را برای عمل تکی لازم ندارند. `ConcurrentHashMap` خواندن و به‌روزرسانی ساده را همزمان تحمل می‌کند. عمل مرکب «اگر نبود بگذار» را با `compute` انجام بده، نه با `get` و بعد `put`. `CopyOnWriteArrayList` خواندن را ارزان و نوشتن را با کپی کل آرایه گران می‌کند. iterator آن تصویر لحظهٔ ساخت است و fail-fast نیست. `BlockingQueue` دست‌به‌دست کردن بین نخ تولید و مصرف است: اگر جا نیست یا چیزی نیست، نخ منتظر می‌ماند.

`Executor` نخ را از کار جدا می‌کند. استخر با اندازهٔ ثابت اگر پر شود، کار تازه صف می‌شود. اگر خود کارها منتظر نتیجه‌ای باشند که باید روی همان استخر اجرا شود، deadlock استخر است. `shutdown` کار تازه نمی‌پذیرد و کارِ پذیرفته‌شده را تمام می‌کند. `shutdownNow` تلاش می‌کند نخ‌های در حال اجرا را interrupt کند و صفِ شروع‌نشده را برمی‌گرداند. `Future.get` تا آماده شدن نتیجه بلوکه می‌شود و exception کار را در `ExecutionException` می‌پیچد.

`CompletableFuture` چند کار را بدون نخِ اختصاصیِ دستی ترکیب می‌کند. `thenCompose` کار بعدی را به نتیجهٔ قبلی وصل می‌کند. `thenCombine` دو نتیجهٔ مستقل را یکی می‌کند. این هنوز مدل thread و قفل را حذف نمی‌کند. فقط زنجیره را خواناتر می‌کند.

virtual thread در Java 21 با `Thread.ofVirtual()` ساخته می‌شود. برای انتظار، مثلاً I/O، ارزان است و استخر نمی‌خواهد. اگر `main` زود تمام شود، چون virtual thread پیش‌فرض daemon است، ممکن است کارش را نبینی. `join` کن. در Java 21 اگر virtual thread داخل بلوک `synchronized` بلوکه شود، به carrier pin می‌شود و مزیتش برای همان مدت از بین می‌رود. قفل صریح `ReentrantLock` این pin را ندارد. پس برای کدی که داخلش انتظار هست، روی virtual thread مانیتور `synchronized` را دور انتظار نگه ندار.

structured concurrency در Java 21 هنوز preview است و API پایدار ۲۱ نیست. `StructuredTaskScope` را در کد ۲۱ بدون `--enable-preview` حساب نکن، و حتی با آن، جزئیات API را پایدار فرض نکن.

deadlock را از روی thread dump بشناس، نه از روی حدس. دو نخ `BLOCKED` که هر کدام «waiting to lock» مانیتوری است که دیگری «locked» کرده، همان دور است. dump را با `jcmd <pid> Thread.print` یا ابزار خود JDK می‌گیری. لازم نیست پرچم‌ها را حفظ کنی. باید بتوانی صاحب قفل و منتظر قفل را در متن پیدا کنی.

## قاعده

برای «دیده شود» به happens-before تکیه کن: `volatile` برای یک پرچم یا یک انتشارِ شیءِ کامل‌ساخته، قفل برای بخش بحرانی. برای «یکی شود» `count++` را روی متغیر معمولی رها نکن. virtual thread را استخر نکن. در Java 21 داخل `synchronized` کاری که بلوکه می‌شود نگذار. structured concurrency را API پایدار ۲۱ ندان.

## مثال

این پرچم دیده می‌شود، چون نوشتن و خواندن `volatile` رابطهٔ happens-before دارند. خود شمارش را atomic نکن با `volatile`. این فقط انتشار یک وضعیت تمام‌شده است:

```java
class Publish {
    private volatile boolean ready;

    void mark() {
        ready = true;
    }

    boolean seen() {
        return ready;
    }
}
```

شمارش یک‌پارچه، و شروع کار روی virtual thread. `join` می‌گذارد نتیجه قبل از تمام شدن `main` دیده شود:

```java
AtomicInteger count = new AtomicInteger();
Thread worker = Thread.ofVirtual().start(() -> count.incrementAndGet());
worker.join();
```

## اشتباه رایج

`volatile int count` و بعد `count++` از چند نخ. دیده‌شدنِ نوشتن تضمین شده، ولی خواندن-جمع-نوشتن هنوز دو تکه است و حاصل کمتر از انتظار درمی‌آید.

## تمام است وقتی

یک کار را با virtual thread موازی کنی و یک وضعیت مشترک را طوری منتشر کنی که دیده‌شدنش با `volatile` یا قفل برقرار باشد.
